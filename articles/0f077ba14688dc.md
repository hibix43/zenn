ジェネリクスは〜や〜に便利ですよね。しかし、許容するジェネリクスの型を自由に設定できるようにするためにはちょっとしたテクニックを知ることが必要です。そうしたジェネリクスを便利に使えるようにするためのテクニックを紹介します。

## 遭遇した課題

（使用するサーバー通信パッケージにもよりますが）API を扱うとき、レスポンスの `status` を確認せずに、いきなり `body` を取り出すのは危険です。通信エラーやサーバーエラーなど、期待しないレスポンスが返ってくる可能性があるため、まずは `status` を検証し、`body` が存在するかどうかをきちんと確認する必要があります。

このチェックを毎回 RemoteDataSource に書いていると、どうしても重複が生まれます。そこで、**status の確認と、必要に応じて `body` を返す処理をひとつにまとめた共通関数 `validatedBody<T>()` を作りたい**と考えました。

しかし、この“共通化”を実現しようとすると、ジェネリクス `T` の型によって `body` の扱いを分ける必要があることに気づきました。T の違いに応じて適切に振る舞わせたい、というニーズが出てきたのです。

具体的には、次の 3 つのケースを正しく扱える必要があります。

### 1. **T が非 nullable の場合**

- `body` が **null ではない** → `body` を返す
- `body` が **null** → **例外を投げる**
  （非 nullable 型では null を返してはいけないため）

### 2. **T が nullable の場合（例: int?）**

- `body` が値でも null でも、**そのまま返す**

### 3. **T が void の場合**

- 一部の POST / DELETE のように `body` を返さない API がある
- **例外は投げず、返す値も特に必要ない**
- ただし、そのまま `return null;` はできないため、ここが実装上のポイントになる

---

この 3 パターンすべてを満たす **T に応じて適切に振る舞うことができる実装**
──これが今回の“小さな小さなテクニック”です。

## 課題を解決した小さなテクニック

```dart
T validatedBody<T>(Response<T> response) {
  // 0) status が正常でない場合は body を確認する前に例外をスローする
  if (!response.isSuccessful) {
    throw InvalidResponseStatusException();
  }

  // 1) body が null かつ T が null を許容しない型なら例外をスローする
  if (response.body == null && (null is! T)) {
    throw InvalidResponseFormatException(
      'body should not be null',
      innerException: response.error,
    );
  }

  // 2) body が null かつ T が null を許容する型なら null を返す
  //    （T が int? / dynamic / void のときはこちらに入る）
  if (response.body == null && (null is T)) {
    return null as T;
  }

  // 3) それ以外は body が null ではないことが保証されるので返す
  return response.body!;
}
```
