Riverpod2.x までは dispose 後であっても Ref にアクセスすることができました。しかし、こうした挙動は本来想定されていない使い方であり、Riverpod3 では dispose 後に Ref にアクセスすると UnmountedRefException が発生するようになりました。
Riverpod2.x で開発していたアプリケーションをそのまま Riverpod3 に移行すると、`await ref.read(hogeProvider.future)` のようなコードが UnmountedRefException を引き起こすことがあります。こうした記述はよく見られる実装であり、Riverpod3 への移行において大きな障壁となることがあります。
この記事では、なぜこうした記述が UnmountedRefException を引き起こすのか、そしてどのように書き換えるべきなのか、購読と監視の観点から解説しようと思います。

## 前提

- Riverpod 3.5.0 で動作を確認しています
- `@riverpod` で生成される Provider は、標準で `autoDispose` になります。本記事では、特に記述がない限り、登場する Provider はすべて `autoDispose` であるとします
- 本記事では、Provider が dispose されることで発生する UnmountedRefException を扱います
  - なお、dispose とは別に、依存先の変化で build がやり直されたときにも、古い build の `ref` を使うと UnmountedRefException が発生します
    - `autoDispose` かどうかは関係ありません。keepAlive でも発生します
    - この例外は Riverpod が捨てるため、表には出ません
    - 詳しくは「[build のやり直しで起きる UnmountedRefException は表に出ない](#build-のやり直しで起きる-unmountedrefexception-は表に出ない)」で後述

### 4. keepAlive を使用する

`@Riverpod(keepAlive: true)` を使用して、そもそも dispose されないようにする方法です。これにより、非同期処理の完了後に Ref にアクセスしても UnmountedRefException は発生しません。ただし、keepAlive な Provider の使用は、非同期処理の結果を画面に反映するだけの Provider に対しては過剰な場合が多いです。keepAlive な Provider は、アプリケーション全体で共有されるような Provider に対してのみ使用しましょう。

また `ref.keepAlive()` を使用して、必要なタイミングでのみ dispose されないようにすることもできます。 返り値の `KeepAliveLink` を保持している間は dispose されず、`KeepAliveLink.close()` を呼ぶと dispose されるようになります。（逆に言えば `close()` を呼ばない限り dispose されないため、意図しないメモリリークに注意）

:::message alert
try/catch でキャッチすればよいのでは、と思った方もいるかもしれません。しかし、これは回避策にはなりません。UnmountedRefException は `@internal` な例外であり、アプリケーションコードでキャッチすることは推奨されていません。
画面で発生したように見えても、実際はその画面から呼び出された Provider/Notifier 内で、すでに dispose された Ref にアクセスしていることがほとんどです。try/catch で握りつぶすのではなく、発生箇所の Provider/Notifier を上記の方法で修正しましょう。
:::
