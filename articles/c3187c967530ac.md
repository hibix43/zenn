## はじめに

私の担当するプロジェクトでは、`build_runner`を用いたコード生成を活用するパッケージをいくつも使っています。`riverpod_generator`もその一つです。ところが、`riverpod_generator`が3.x未満だと`build`パッケージが2.xのままで、他のコード生成パッケージのアップデートがいつまで経ってもできない状態でした。この依存関係の問題を解決するため、大変そうだとは思いつつもRiverpod 3.0への移行を決断しました。

実際、移行作業は想像以上に大変でした。だからこそ、同じ課題に直面している方の助けになればと思い、この記事にまとめることにしました。

この記事では、Riverpod 3.0への移行で遭遇した問題とその対処方法をまとめています。移行のすべてを解説するガイドではなく、特に対応に悩んだポイントや公式ドキュメントに記載されていない点を中心に扱います。そのため、オフライン機能やMutationsといった新機能の説明はしません。

移行の基本的な手順は、以下の公式ドキュメントを参照してください。ただし、これらに記載のない変更や、記載があっても適切な対応方法が明確でない点が多く存在します。本記事がその補完になれば幸いです。

- [What's new in Riverpod 3.0 | Riverpod](https://riverpod.dev/ja/docs/whats_new)
- [Migrating from 2.0 to 3.0 | Riverpod](https://riverpod.dev/ja/docs/3.0_migration)

誤字・脱字や事実と異なる記述があれば、ぜひコメントで指摘してください。

## 主要な変更点

### 1. NotifierProviderの命名規則変更

`riverpod_generator`を使用している場合、Notifierクラスから生成されるProviderの命名規則が変更されました。

```dart
@riverpod
class HogeNotifier extends _$HogeNotifier { }
```

上の例だと Riverpod 2.x では `hogeNotifierProvider` という名前で生成されていましたが Riverpod 3.0 からは `hogeProvider` になります。

#### 一時的な回避策

`build.yaml` で設定を変更することで、これまでの命名規則を維持できます。

```yaml
targets:
  $default:
    sources:
      - $package$
      - pubspec.yaml
      - lib/**
    builders:
      riverpod_generator:
        options:
          # xxxNotifierProvider の名前を維持するため、空文字列を指定する
          provider_name_strip_pattern: ""
```

<https://pub.dev/packages/riverpod_generator#global-configuration>

:::message
一時的に `""` を指定しておくと1つのPRの変更量を減らせます。その後に名前変更だけのPRを作ると、レビューがしやすく、おすすめです。
:::

### 2. @Dependenciesアノテーションの追加(riverpod_lint)

`ProviderScope#override`でオーバーライドしているProviderに画面から依存する場合は、`@Dependencies([overridenHoge])`を付与する必要があります。

これまでもProviderに対して `@Riverpod(dependencies: [overridenHoge])` とすることはありましたが、画面からもこれを追記する必要が出てきました。生成された後の `overridenHogeProvider` ではなく、生成対象の関数を指定する必要があることを覚えておきましょう。

```dart
import 'package:riverpod_annotation/experimental/scope.dart';

@Dependencies([overridenHoge])
class HogeScreen extends ConsumerWidget {}
```

quick fixで追加できるため、エラーが表示されたら指示に従って追加するのがおすすめです。

### 3. AsyncValue#valueの名前変更

`AsyncValue`の`value`プロパティが削除され、`valueOrNull`が`value`に改名されました。

```dart
// Before (Riverpod 2.x)
final value = asyncValue.valueOrNull;

// After (Riverpod 3.0)
final value = asyncValue.value; // valueOrNullがvalueに改名された
```

quick fixでは修正されません。一括置き換えで対応しましょう。

<https://riverpod.dev/ja/docs/whats_new#asyncvalue>

### 4. Override型のインポート変更

Override型を使用する場合、新しいインポート文が必要になりました。

```dart
import 'package:riverpod_annotation/riverpod_annotation.dart';
// もしくは
import 'package:hooks_riverpod/misc.dart';
```

### 5. ProviderContainer.test()の追加

[`ProviderContainer.test()`](https://riverpod.dev/ja/docs/whats_new#providercontainertest)が追加されました。これはテスト用のコンテナを簡単に作成できるヘルパーです。

これまで同じようなユーティリティ関数を作るよう公式ドキュメントにも記載がありましたが、その必要がなくなりました。（←本当か？）

```dart
// Before (Riverpod 2.x)
// ユーティリティ関数を作っておく
ProviderContainer createContainer({
  List<Override> overrides = const [],
}) {
  final container = ProviderContainer(overrides: overrides);
  addTearDown(container.dispose);
  return container;
}
// 使用例
final container = createContainer(
  overrides: [
    countProvider.overrideWithValue(3),
  ]
);


// After (Riverpod 3.0) - 上記と同じ動作
final container = ProviderContainer.test(
  overrides: [
    countProvider.overrideWithValue(3),
  ]
);
```

ただし、後述するように私の担当するプロジェクトでは、retry無効化のために既存のユーティリティ関数を改修する形で使用し続けています。

### 6. 同一引数で二重にオーバーライドしているとエラーになる

同一引数で二重にオーバーライドすると、以下のエラーが発生するようになりました。

```txt
Tried to override a provider twice within the same container
```

私はテストコードにて、この問題に遭遇しました。setUpと各テストケースで二重にオーバーライドしていないか確認しましょう。

### 7. AutoDisposeNotifier/FamilyNotifierのインターフェース変更

手動実装のみに影響があります。`riverpod_generator`を使用している場合は、特に対応は不要です。

<https://riverpod.dev/ja/docs/whats_new#autodispose-interfaces-are-removed>

### 8. setState() or markNeedsBuild()エラー

VSCode や Cursor にて All Exceptions にチェックが入っていると、このエラーが発生することがあります。未だに解決していません。Issue を watch しておきましょう。

<https://github.com/rrousselGit/riverpod/issues/4285>
<https://github.com/rrousselGit/riverpod/issues/4381>

### 9. NotifierのMock作成方法の変更

これまで成功していたNotifierのMockの書き方が、Riverpod 3.0では動かなくなりました。
`Null check operator used on a null value` が発生します。

```dart
// Before (Riverpod 2.x) - これは動かなくなった
class MockHogeNotifier with Mock implements HogeNotifier {}
```

#### 9.1 ドキュメントに記載されているNotifierのMock方法

新しい書き方では、生成された`_$HogeNotifier`を`extends`するようにして書く必要があります。

```dart
// After (Riverpod 3.0)
class MockHogeNotifier extends _$HogeNotifier with Mock implements HogeNotifier {}
```

<https://riverpod.dev/ja/docs/how_to/testing#mocking-notifiers>

:::message alert
名前からわかるように`_$HogeNotifier`がprivate classであるため、以下の問題があります

- Mockのコードを`test/`ではなく`lib/`に書く必要がある
- `mockito`を`dev_dependencies`から`dependencies`に移動する必要がある
:::

#### 9.2 手動実装のNotifierクラスを頼る方法

`_$HogeNotifier`を使用する以外の方法として以下のように`riverpod_generator`を使用しない実装のために存在する`Notifier/AsyncNotifier`クラスを使用することでもNotifierのMockを実現することが可能です。

```dart
import 'package:hooks_riverpod/hooks_riverpod.dart' show AsyncNotifier;

class MockHogeNotifier extends AsyncNotifier<HogeState> with Mock implements HogeNotifier
```

とはいえ、NotifierのMockは推奨されていませんし、`riverpod_generator`を使用しながらこの方法を取るのはあまり適切ではないように見えます。（これは偶然かもしれませんが、`AsyncNotifier`のインポートがquick fixで解決できなかったりもしました）

なるべく、NotifierをMockすることは避けましょう。そして、`build`のため（すなわち、notifierProviderの状態を書き換えるため）だけであれば、次に紹介する`overrideWithBuild`を使用するようにしましょう。

#### 9.3 これまでのNotifierのMock実装が `Null check operator used on a null value` になる理由

これまでのように`class MockHogeNotifier with Mock implements HogeNotifier {}`という書き方で実装されたMockHogeNotifierを使用してテストを実行すると`Null check operator used on a null value`が発生します。このエラーは強制アンラップしようとした値がnullだったことを示す、典型的なエラーですが、私は最初どこでエラーが発生しているのか全くわからずにいました。

その原因は生成される`_$HogeNotifier`の実装を見るとわかります。`_$HogeNotifier`には`runBuild`というメソッドが実装されています。これがないと（`runBuild`の中の`handleValue(ref,created)`が実行されず）初期状態を計算する中で`AsyncLoading`から`AsyncData`に切り替わっていきません。そして、（`AsyncData`を期待した）状態の強制アンラップがエラーを起こすようになっていました。

:::details エラー発生までの具体的な流れ

1. 前提として`(Async)Notifier#value`の初期値は`AsyncLoading`(実装上は`AsyncValue.loading()`)になっている
2. `ProviderElement#mount`（あるいは`_performRebuild`）では`ProviderElement#buildState`を呼び出す
3. `ProviderElement#buildState`では`$ClassProviderElement#create`を呼び出す
4. `$ClassProviderElement#create`では下記の分岐が存在する
   - `overrideWithBuild` によって`build`が`override`されている場合：`$ClassProviderElement#handleValue`を呼び出す
   - そうではない場合：`AnyNotifier#runBuild`を呼び出す
      - この`AnyNotifier#runBuild`を生成した`$_HogeNotifier`が`override`しており、`_$HogeNotifier#runBuild`では`$ClassProviderElement#handleValue`を呼び出している
5. `$ClassProviderElement#handleValue`は`Notifier/AsyncNotifier`それぞれに向けて`override`されている
   - `$NotifierProviderElement#handleValue`では`ElementWithFuture#value`(`ProviderElement#value`)を`AsyncData`で上書きする
   - `$AsyncValueProviderElement#handleValue`では`ElementWithFuture#handleFuture`を呼び出している
6. `ElementWithFuture#handleFuture`は`ElementWithFuture#_handleAsync`を呼び出す
7. `ElementWithFuture#_handleAsync`は`ElementWithFuture#onValue`あるいは`ElementWithFuture#onData`を呼び出す
8. `ElementWithFuture#onValue`は`ElementWithFuture#onData/onLoading/onError`を呼び出す
9. `ElementWithFuture#onData/onLoading/onError`はいずれも`ElementWithFuture#asyncTransition`を呼び出す
10. `ElementWithFuture#asyncTransition`は`ProviderElement#value`を新しい状態に上書きする

長々と流れを記述していますが、ポイントとしては **`_$HogeNotifier#runBuild`が見つからないと`$ClassProviderElement#handleValue`が呼び出されないこと** です。`$ClassProviderElement#handleValue`を呼び出さないことは`$ClassProviderElement#value`を更新しないことになります。

そして、`ProviderElement#buildState`（3.）では`$ClassProviderElement#create`（4.）を呼び出した後、`ProviderElement#_notifyListeners`を呼び出します。この`ProviderElement#_notifyListeners`の中で`ProviderElement#resultForValue`を実行しますが、これは`AsyncLoading`だと`null`を返す実装になっています。この結果に対して強制アンラップを実行しているため、エラーになるのです。

```dart

    AsyncValue<ValueT> newStateValue,
    AsyncValue<ValueT>? previousStateValue, {
    bool checkUpdateShouldNotify = true,
    bool isFirstBuild = false,
  }) {
    if (kDebugMode && !isFirstBuild) _debugAssertNotificationAllowed();

    final newState = resultForValue(newStateValue)!; // ここが問題
```

<https://github.com/rrousselGit/riverpod/blob/b668bb10ab2eae8fb9544a040e7afbce238de173/packages/riverpod/lib/src/core/element.dart#L762-L770>


そして、`riverpod_generator`を使用せず手動で`Notifier`を実装するための`Notifier`クラスにはもちろん、`runBuild`が実装されており、`handleValue`が実行されるようになっています。（だから、9.2のように`Notifier`クラスを用いて`Notifier`のMockを作成することができる）

### 10. overrideWithBuildの活用

Riverpod 3.0では[`overrideWithBuild`](https://riverpod.dev/ja/docs/whats_new#notifierprovideroverridewithbuild)が追加され、`build`メソッドだけをカスタマイズできるようになりました。NotifierのMockを作成する代わりに、`overrideWithBuild`を使用することを推奨します。

```dart
// Before (Riverpod 2.x) - Mockを作成していた
class MockLocalUserDataNotifier extends StreamNotifier<UserData>
    with Mock
    implements LocalUserDataNotifier {
  MockLocalUserDataNotifier({required this.stream});

  final Stream<UserData> stream;

  @override
  Stream<UserData> build() {
    return stream;
  }
}

final container = createContainer(
  overrides: [
    localUserDataProvider.overrideWith(
      () => MockLocalUserDataNotifier(
        stream: Stream.value(UserData(...))
      )
    )
  ]
);


// After (Riverpod 3.0) - overrideWithBuildを使用
final container = ProviderContainer.test(
  overrides: [
    localUserDataProvider.overrideWithBuild((_, __) => Stream.value(UserData(...))),
  ]
);
```

どうしても`build`以外のメソッドをMockしたい時だけ、上記のMockNotifierを活用しましょう。`build`以外のメソッドをMockする必要があるときは、そのメソッドの中で活用しているであろう、RepositoryをMockすることやProviderをoverrideすることで解決できないか検討しましょう。

### 11. 自動リトライ

Riverpod3では[自動リトライ機能](https://riverpod.dev/ja/docs/whats_new#automatic-retry)が追加されました。Providerの初期化が失敗しても成功するかdisposeされるまで自動的に再計算を実行します。これでネットワークエラーなどの一時的な問題の対処が簡単になります。

しかし、この自動リトライ機能はテストにおいて非常に厄介です。`overrideWithBuild`を活用するなどして初期値の計算中で例外をスローしても、自動リトライ機能が動作するため、直ちに`AsyncError`にならず、検証がやりにくくなってしまいます。

具体的には `TimeoutException after 0:00:30.000000: Test timed out after 30 seconds.` というタイムアウトが発生しました。これは、自動リトライ機能がデフォルトで最大約50秒かかる（0.2sから始まって6.4sまで間隔を広げつつ10回）ためです。これに対し、[Dartのテストでは特に指定がない場合30秒でタイムアウト](https://pub.dev/packages/test#timeouts)します。

こうした事態を避けるため、テストでは`ProviderContainer(ProviderScope)#retry`にて`null`を返すよう変更して自動リトライ機能を無効化しておくと良いでしょう。

```dart
final container = ProviderContainer.test(
  overrides: [
    localUserDataProvider.overrideWithBuild((_, __) {
      throw Exception('Could not find the user data!');
    })
  ],
  retry: (retryCount, error) {
    // 常にリトライを行わないようにする
    // retryCount の回数や error の種類でリトライの有効性を変更することもできる
    return null;
  }
);
```

また、こうした自動リトライ機能の無効化を毎テストに書くのは面倒ですよね。となると、前述のようにユーティリティ関数を改修して使い続けることが便利だったりします。

```dart
ProviderContainer createContainer({
  List<Override> overrides = const [],
}) {
  final container = ProviderContainer.test(
    overrides: overrides,
    retry: (retryCount, error) {
      // 常にリトライを行わないようにする
      return null;
    }
  );
  return container;
}
```

### 12. keepAliveとautoDisposeの関係(riverpod_lint)

keepAliveのProviderが依存するProviderは、すべてkeepAliveとしてマークする必要があります。

keepAliveのProviderAがautoDisposeのProviderBに依存している場合、警告が表示されます。

取る選択肢は2つです：

- ProviderAをautoDisposeに変更する
- ProviderBをkeepAliveにする

もしProviderBがProviderCに依存している場合、ProviderCも同様に対処する必要があります。

### 13. UnmountedRefExceptionとその対処

Riverpod 3.0では、Providerのライフサイクル管理が厳格になり、dispose後に`ref`や`notifier`にアクセスすることが禁止されました。アクセスしようとすると、`UnmountedRefException`が発生します。

:::message
厳密にはそのProviderを参照することがなくなってから、次のrebuildがきて、初めてdisposeされます。そのため、必ず再現するものではなかったりします。しかし、`ref/notifier`にアクセスする前に`await Future.delayed(const Duration(seconds: 1))`とするだけでも再現するようになったりして非常に不安定であるため、下記の事例のように問題があるとされるパターンに該当する箇所は全て実装を変更しておくことをおすすめします。
:::

:::message
この節で説明する問題はどれも`keepAlive:true`としておくことでも解決可能です。ただ、当然ですが`keepAlive:true`のProviderはメモリに残り続けることになるため、あまり多くは使わないほうが良いでしょう。本当にこのProviderは状態を維持し続けるべきなのか？という観点に立って判断しましょう。
:::

#### 発生するエラー

```txt
threw StateError:<Bad state: The provider hogeProvider was disposed during loading state, yet no value could be emitted.>
```

```txt
threw UnmountedRefException:<Cannot use the Ref of hogeProvider after it has been disposed. This typically happens if:
                - A provider rebuilt, but the previous "build" was still pending and is still performing operations.
                  You should therefore either use `ref.onDispose` to cancel pending work, or
                  check `ref.mounted` after async gaps or anything that could invalidate the provider.
                - You tried to use Ref inside `onDispose` or other life-cycles.
                  This is not supported, as the provider is already being disposed.
                >
```

#### 正攻法の修正案

これを回避するための正攻法は`ref.mounted`で事前にマウントの状態（＝disposeされていないか）を確認することです。Providerがdisposeされていた場合、後続の処理を実行しなくても良いケースでは、`ref.mounted`を用いてスキップすることでエラーを回避できます。

<https://riverpod.dev/ja/docs/whats_new#refmounted>

```dart
// Notifier に実装されるメソッドのイメージ
Future<void> storeNewValue() async {
  final value = await fetch();
  // ref.mounted が false なら無視
  if (ref.mounted) {
    final repository = ref.read(repositoryProvider);
    await repository.store(value);
  }
}
```

この対応を見た時、そもそもスキップしても良いケースなんてあるのかと疑問に思いました。しかし、いざ`UnmountedRefException`が発生する箇所を動作確認していくと、確かにスキップして良いケースがいくつか見つかりました。
例えば、あるNotifierのメソッドの中で非同期処理を実行した後に`state = xxx`と自身の状態を書き換えていました。しかし、このNotifier(Provider)をwatchしている画面とメソッドを呼び出す画面は分かれていて、その場で状態を書き換えなくても良かったのです。（そして、watchする画面をあらためて開くときは、buildメソッドが再計算されるようになっていた）

#### `ref.mounted`では解決できない発生箇所

`ref.mounted`でdisposeされていれば`ref/notifier`にアクセスしない、とするのが最も簡単ではありますが、そうしてしまうと挙動が変わってしまって不具合が起きてしまう。こうしたケースの方がほとんどだと思います。

また `ref.mounted` で解決しようがないエラーの発生箇所も存在し、特別な対応を取ることを推奨されているものもあります。`ref.mounted`では解決できない発生箇所とその対応策について説明します。

#### `await ref.read(hogeProvider.future)` を使用している箇所

FutureProviderをはじめとした状態が非同期的に計算されるProviderの値を取得する場合、`.future`を使用して取得する側で`await`して通常の非同期処理と同様に扱うことはよくある実装ですよね。しかしRiverpod3では、この実装が機能しなくなりました。

これに対して、Riverpodの開発者であるRemiさんは、`await ref.read(hogeProvider.future)`とするのをやめて、以下のように書き換えることを推奨しています。（[ドキュメントにこの変更を記載するIssue](https://github.com/rrousselGit/riverpod/issues/3745)が建てられています）

```dart
final subscription = ref.listen(hogeProvider.future, (p, n) {});
final value = await subscription.read();
subscription.close();
```

一時的にProviderを監視してdisposeされないようにしておき、状態を取得した後に監視を破棄する、という実装です。これなら、状態を取得しようとしている最中にdisposeされてしまう、という問題は解決できますよね。

確かに上記のコードで問題は解決されますが、毎回こうした実装を書くのは面倒です。また、`subscription.close()`を呼び出すことを忘れてしまいそうです。そのため、以下のようなextensionを作成すると便利です。

```dart
import 'package:hooks_riverpod/hooks_riverpod.dart';
import 'package:hooks_riverpod/misc.dart' show Refreshable;

extension RefExtension on Ref {
  Future<T> readFirst<T>(Refreshable<Future<T>> listenable) async {
    final subscription = listen(listenable, (p, n) {});
    try {
      return await subscription.read();
    } finally {
      subscription.close();
    }
  }
}

extension WidgetRefExtension on WidgetRef {
  Future<T> readFirst<T>(Refreshable<Future<T>> listenable) async {
    final subscription = listenManual(listenable, (p, n) {});
    try {
      return await subscription.read();
    } finally {
      subscription.close();
    }
  }
}
```

命名は[こちらのIssueコメント](https://github.com/rrousselGit/riverpod/issues/3745)を参考にしました。他にも`readAsync`という命名がIssueではよく見られました。もっといい名前を思いついた！という方はコメント欄等々でぜひシェアして欲しいです。

:::details なぜ`MutationTarget`に対して`extension method` を実装しないのか
Riverpod3から登場した`MutationTarget`に対して`extension method`を書くようにすると実装がまとまって嬉しいです。

```dart
import 'package:hooks_riverpod/experimental/mutation.dart' show MutationTarget;
import 'package:hooks_riverpod/misc.dart' show Refreshable;

// Ref/WidgetRef/ProviderContainerにreadFirstメソッドが追加される
extension MutationTargetExtension on MutationTarget {
  Future<T> readFirst<T>(Refreshable<Future<T>> listenable) async {
    final subscription = container.listen(listenable, (p, n) {});
    try {
      return await subscription.read();
    } finally {
      subscription.close();
    }
  }
}
```

しかし、このように実装すると同じく`MutationTarget`に分類される`ProviderContainer`にまで`readFirst`メソッドを追加してしまいます。`ProviderContainer`は（Flutterアプリの開発において）テストの中で使用されるものです。そして、テストではこの`readFirst`相当の実装は不要です（理由は後述）。使われるはずのない`ProviderContainer`にまで`readFirst`を実装されることに違和感を覚え、上記のように`Ref`と`WidgetRef`で別々に実装をしました。（とはいえ、強く反対するものでもないです…）

:::

一見すると不具合のようにも見えますが、これまでdispose後であってもRefにアクセスできていたことが問題であり、この挙動が期待される動作だということです。粛々と対応しましょう。（できれば型の段階で`ref.read(provider.future)`と書けないようになってほしいですが…）

##### なぜテストでは`await ref.read(hogeProvider.future)`が機能し続けるのか

Riverpod3から機能しなくなった`await ref.read(hogeProvider.future)`も実は、テストでは機能し続けます。理由はテストコードをよく見てみればわかります。テストでは以下のように書くことが多いです。

```dart
final container = ProviderContainer();
addTearDown(container.dispose);
final value = await ref.read(hogeProvider.future);
expect(value, 3);
```

この`addTearDown(container.dispose)`が重要です。これはテストの終了時になって初めて`container`をdisposeします。しかし、本番ではProviderが必要とされなくなったら、直ちにdisposeされます。このdisposeタイミングの違いが、テストと本番の挙動の違いであり、テストでは`.future`が機能し続ける理由です。

なお、`ProviderContainer.test()`も中身は全く同じです。

<https://github.com/rrousselGit/riverpod/blob/f4c59d00f2eed63267cb46d23335000cf44341dc/packages/riverpod/lib/src/core/provider_container.dart#L810-L826>

#### Providerの外でRefを使用できるようにしている箇所

今回、対応が最も大変だったのがこのProviderの外でRefを使用している箇所のリファクタリングです。私の担当しているアプリではあらゆる箇所でRefを活用して依存関係や状態の取得を行っていました。薄々「良くない実装だよなあ」とは思っていたものの、今回、明確に動かなくなったことで大規模な改修を迫られることになりました。もし、同じような実装を採用しているようでしたら、これを機に考え直すことをおすすめします。

この記事では最後に実際に私が直面したProviderの外でRefを使用している実装の代表例とその改善策をご紹介します。

##### classにRefを渡す実装

classにRefを持たせる実装を全て改修しました。Refがサービスロケーターのような扱いをしている実装です。このクラスのインスタンスを状態としてもつProviderを`ref.read`してインスタンスを得たとしても、そのインスタンスのメソッドを実行するときにはProviderはdisposeされているため、インスタンスの持つRefは機能しません。

```dart
// before
class Service {
  const Service(this.ref);

  final Ref ref;

  Future<void> store(Entity entity) async {
    final converter = ref.read(converterProvider);
    final converted = await converter.convert(entity);
    final repository = ref.read(repositoryProvider);
    await repository.store(converted);
  }
}

@riverpod
Service service(Ref ref) => const Service(ref);

// この ref.read 直後から serviceProviderのRefにアクセスすることはできない
final service = ref.read(serviceProvider);
await service.store(entity);
```

コンストラクタにて依存関係を渡す「Dependency Injection」に修正しましょう。

```dart
// after
class Service {
  const Service(this.repository, this.converter);

  final Repository repository;
  final Converter converter;

  Future<void> store(Entity entity) async {
    final converted = await converter.convert(entity);
    await repository.store(converted);
  }
}

@riverpod
Service service(Ref ref) async {
  final repository = ref.watch(repositoryProvider);
  final converter = ref.watch(converterProvider);
  return const Service(repository, converter);
}

final service = ref.read(serviceProvider);
await service.store(entity);
```

対応が必要な箇所は`final Ref`で検索すると見つけやすいです。良くないと思っていても、Refを渡す方がずっと簡単で、そこに甘えてしまっていたように思いました。今後はlintルールでも作って`final Ref`と書けないようにしておきたいです。

##### クロージャを返すProvider

もう一つ、私が担当しているアプリで問題になった実装の代表例がクロージャを返すProviderでした。何を言っているんだ？と疑問に思われるかもしれませんが、まずは以下のコードを見てください。

```dart
// before
@riverpod
Future<void> Function(Entity) useCase(Ref ref) {
  return (entity) async {
    final drift = ref.read(driftProvider);
    final service = ref.read(serviceProvider);
    await drift.transaction(() async {
      await service.store(entity);
    });
  }
}

onPressed: () async {
  try {
    isLoading.value = true;
    // useCaseProviderの状態を取得してFuture<void> Functionを得ることはできるが、
    // その中でRefにアクセスすることはできない
    await ref.read(useCaseProvider)(entity);
  } catch {
    showErrorDialog(context);
  } finally {
    isLoading.value = false;
  }
}
```

UseCaseの実装をProviderに全乗っかりするという実装です。 ~~（見た目はすごく綺麗だと思いませんか？見た目は。）~~ もちろん、これも機能しません。こちらも同じように依存性を注入してあげましょう。

```dart
class UseCase {
  const UseCase(this.service, this.drift);

  final Service service;
  final AppDatabase drift;

  Future<void> call(Entity entity) async {
    await drift.transaction(() async {
      await service.store(entity);
    });
  }
}

@riverpod
UseCase useCase(Ref ref) {
  final service = ref.watch(serviceProvider);
  final drift = ref.watch(driftProvider);
  return const UseCase(service, drift);
}

onPressed: () async {
  try {
    isLoading.value = true;
    await ref.read(useCaseProvider)(entity);
  } catch {
    showErrorDialog(context);
  } finally {
    isLoading.value = false;
  }
}
```

:::details 依存関係の取得以外にも`ref`を使用しているケースでは？
上記のUseCaseの例ではServiceと（トランザクション用の）AppDatabaseを必要とするために`ref`を用いていました。しかし、`ref`の使い道は単に依存関係を取得するだけではないはずです。具体的にいうと`ref.invalidate`を実行して特定のProviderの状態を再計算させたり、`ref.read(provider.notifier).changeValue()`のようにNotifierのメソッドを実行したりすることもありますよね。こうした処理はどのように記述すれば良いのでしょうか？私の対応は以下の2つでした。

1. `ref.invalidate`は画面から実行する
2. `notifier`のメソッドをUseCaseから呼び出すのではなく、NotifierからUseCaseを実行するようにする

`ref.invalidate`は画面の状態として再計算が必要かどうかに関わるものです。そのため、画面から実行するようにしても違和感はないと判断しました（pull-refreshで`ref.invalidate`を実行することなどはごく一般的な実装ですよね）

NotifierからUseCaseを実行することもレイヤーの上下関係(?)を考えれば自然なことです。Notifierはあくまで画面にとって必要なものであり、ビジネスロジックの置き場所ではありません（本当に小さなプロジェクトでは置き場所になっていても自然ですが）。

正直、2.はともかく1.に関してはUseCaseとセットにして実装ができていて良かったのですが、仕方がないですね。（何かいい実装があれば教えてください）
:::

#### 改修を迫られて思ったこと

今回、Riverpod 3.0になって期待通りに動かないことによって、classにRefを持たせる実装やクロージャを返すProviderの実装を変更する必要に迫られました。

しかし、これをきっかけに、**Riverpodは状態管理とDIの「ツール」であり、UseCase/Service/RepositoryといったUIと関係のないロジック部分に採用するべきではない**と再認識しました。（UseCase/Service/Repositoryのインスタンスを返すプロバイダーを作るべきではない、ということではないです。サービスロケーターのようにRepositoryの中にまで組み込むべきではないという話）

ビジネスロジックのテストに`ProviderContainer/Scope`を用いなければならないのだとしたら、それはビジネスロジックの実装として適切ではありません。何らかの理由でRiverpodをアプリから剥がしたいとなったとき、ロジック部分がそのまま使用し続けられるような実装が理想です。

## まとめ

Riverpod 3.0への移行では、以下の点が主な変更点でした

1. **命名規則の変更** - NotifierProviderの生成名が変更
2. **依存関係の明示** - @Dependenciesアノテーションの追加
3. **テスト周りの改善** - ProviderContainer.test()やoverrideWithBuildの追加
4. **ライフサイクル管理の厳格化** - UnmountedRefExceptionへの対処が必要

特に`UnmountedRefException`への対応は、Riverpodをどのレイヤーでどのように使用すべきかを見直す良い機会となりました。

移行作業では、まず明確な変更点に対応し、その後にテスト周りの調整やアーキテクチャの見直しを行うと進めやすいでしょう。
