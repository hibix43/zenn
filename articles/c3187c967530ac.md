Riverpod3移行が大変だった。共有したい。移行する中で遭遇した問題、それに対する対応をまとめる。移行のすべてを解説する記事ではない。→より丁寧に。文章でかく

以下が公式ドキュメントとして存在しますが、こちらに記載のない変更や記載があってもどのように対応するのが適切なのか記載されていない点が多く存在します。
<https://riverpod.dev/ja/docs/whats_new>
<https://riverpod.dev/ja/docs/3.0_migration>

## 検証した環境

```yaml
environment:
  flutter: 3.35.5
  sdk: ">=3.9.2 <4.0.0"

dependencies:
  hooks_riverpod: ^3.0.3
  riverpod_annotation: ^3.0.3

dev_dependencies:
  custom_lint: ^0.8.0
  riverpod_generator: ^3.0.3
  riverpod_lint: ^3.0.3
```

## 主要な変更点

### 1. NotifierProviderの命名規則変更

`riverpod_generator`を使用している場合、Notifierクラスから生成されるProviderの命名規則が変更されました。

```dart
@riverpod
class HogeNotifier extends _$HogeNotifier {
  @override
  Future<HogeState> build async {
    final repository = ref.watch(hogeRepositoryProvider);
    final status = await repository.fetchStatus();
    return HogeState.initial(status: status);
  }
}
```

上の例だと Riverpod 2.x では `hogeNotifierProvider` という名前で生成されていましたが Riverpod 3.0 からは `hogeProvider` になります。

#### 一時的な回避策

`build.yaml` で設定を変更することで、これまでの命名規則を維持できます。

```yaml
targets:
  $default:
    sources:
      - $package$
      - pubspec.yaml
      - lib/**
    builders:
      riverpod_generator:
        options:
          # xxxNotifierProvider の名前を維持するため、空文字列を指定する
          provider_name_strip_pattern: ""
```

<https://pub.dev/packages/riverpod_generator#global-configuration>

:::message
一時的に `""` を指定しておくと1つのPRの変更量を減らせます。その後に名前変更だけのPRを作ると、レビューがしやすく、おすすめです。
:::

### 2. @Dependenciesアノテーションの追加(riverpod_lint)

`ProviderScope#override`でオーバーライドしているProviderに画面から依存する場合は、`@Dependencies([overridenHoge])`を付与する必要があります。

これまでもProviderに対して `@Riverpod(dependencies: [overridenHoge])` とすることはありましたが、画面からもこれを追記する必要が出てきました。生成された後の `overridenHogeProvider` ではなく、生成対象の関数を指定する必要があることを覚えておきましょう。

```dart
import 'package:riverpod_annotation/experimental/scope.dart';

@Dependencies([overridenHoge])
class HogeScreen extends ConsumerWidget {}
```

quick fixで追加できるため、エラーが表示されたら指示に従って追加するのがおすすめです。

### 3. AsyncValue#valueの名前変更

`AsyncValue`の`value`プロパティが削除され、`valueOrNull`が`value`に改名されました。

```dart
// Before (Riverpod 2.x)
final value = asyncValue.valueOrNull;

// After (Riverpod 3.0)
final value = asyncValue.value; // valueOrNullがvalueに改名された
```

quick fixでは修正されません。一括置き換えで対応しましょう。

<https://riverpod.dev/ja/docs/whats_new#asyncvalue>

### 4. Override型のインポート変更

Override型を使用する場合、新しいインポート文が必要になりました。

```dart
import 'package:riverpod_annotation/riverpod_annotation.dart';
// もしくは
import 'package:hooks_riverpod/misc.dart';
```

### 5. ProviderContainer.test()の追加

`ProviderContainer.test()`が追加されました。これはテスト用のコンテナを簡単に作成できるヘルパーです。

これまで同じようなユーティリティ関数を作るよう公式ドキュメントにも記載がありましたが、その必要がなくなりました。（←本当か？）

```dart
// Before (Riverpod 2.x)
// ユーティリティ関数を作っておく1
ProviderContainer createContainer({
  List<Override> overrides = const [],
}) {
  final container = ProviderContainer(
    parent: parent,
    overrides: overrides,
    observers: observers,
  );

  addTearDown(container.dispose);

  return container;
}
// 利用例
final container = createContainer(
  overrides: [
    countProvider.overrideWithValue(3),
  ]
);


// After (Riverpod 3.0) - 上記と同じ動作
final container = ProviderContainer.test(
  overrides: [
    countProvider.overrideWithValue(3),
  ]
);
```

ただし、後述するように私の担当するプロジェクトでは、retry無効化のために既存のユーティリティ関数を改修する形で利用し続けています。

### 6. 同一引数で二重にオーバーライドしているとエラーになる

同一引数で二重にオーバーライドすると、以下のエラーが発生するようになりました。

```txt
Tried to override a provider twice within the same container
```

私はテストコードにて、この問題に遭遇しました。setUpと各テストケースで二重にオーバーライドしていないか確認しましょう。

### 7. AutoDisposeNotifier/FamilyNotifierのインターフェース変更

手動実装のみに影響があります。`riverpod_generator`を利用している場合は、特に対応は不要です。

<https://riverpod.dev/ja/docs/whats_new#autodispose-interfaces-are-removed>

### 8. setState() or markNeedsBuild()エラー

VSCode や Cursor にて All Exceptions にチェックが入っていると、このエラーが発生することがあります。未だに解決していません。Issue を watch しておきましょう。

<https://github.com/rrousselGit/riverpod/issues/4285>
<https://github.com/rrousselGit/riverpod/issues/4381>

### 9. NotifierのMock作成方法の変更

これまで成功していたNotifierのMockの書き方が、Riverpod 3.0では動かなくなりました。

```dart
// Before (Riverpod 2.x) - これは動かなくなった
class MockHogeNotifier with Mock implements HogeNotifier {}
```

#### 9.1 ドキュメントに記載されているNotifierのMock方法

新しい書き方では、生成された`_$HogeNotifier`を`extends`するようにして書く必要があります。

```dart
// After (Riverpod 3.0)
class MockHogeNotifier extends _$HogeNotifier with Mock {} implements HogeNotifier
```

<https://riverpod.dev/ja/docs/how_to/testing#mocking-notifiers>

:::message alert
名前からわかるように`_$HogeNotifier`がprivate classであるため、以下の問題があります：

- Mockのコードを`test/`ではなく`lib/`に書く必要がある
- `mockito`を`dev_dependencies`から`dependencies`に移動する必要がある
:::

#### 9.2 手動実装のNotifierクラスを頼る方法

`_$HogeNotifier`を利用する以外の方法として以下のように`riverpod_generator`を使用しない実装のために存在する`AsyncNotifier/Notifier`クラスを利用することでもNotifierのMockを実現することが可能です。

```dart
import 'package:hooks_riverpod/hooks_riverpod.dart' show AsyncNotifier;

class MockHogeNotifier extends AsyncNotifier<HogeState> with Mock implements HogeNotifier
```

とはいえ、**そもそもNotifierのMockは推奨されていません**し、`riverpod_generator`を利用しながらこの方法を取るのはあまり適切ではないように見えます。（これは偶然かもしれませんが、`AsyncNotifier`のインポートがquick fixで解決できなかったりもしました）

なるべく、NotifierをMockすることは避けましょう。そして、`build`のため（すなわち、notifierProviderの状態を書き換えるため）だけであれば、次に紹介する`overrideWithBuild`を利用するようにしましょう。

#### 9.3 これまでのNotifierのMock実装が`Null check operator used on a null value`になる理由

これまでのように`class MockHogeNotifier with Mock implements HogeNotifier {}`という書き方で実装されたMockHogeNotifierを利用してテストを実行すると`Null check operator used on a null value`が発生します。このエラーは強制アンラップしようとした値がnullだったことを示す、典型的なエラーですが、私は最初どこでエラーが発生しているのか全くわからずにいました。

その原因は生成される`_$HogeNotifier`の実装を見るとわかります。`_$HogeNotifier`には`runBuild`というメソッドが実装されています。詳しい説明は省きますが、これがないと（`runBuild`の中の`handleValue(ref,created)`が実行されず）初期状態を計算する中でAsyncLoadingからAsyncDataに切り替わっていきません。そして、（`AsyncData`を期待した）状態の強制アンラップがエラーを起こすようになっていました。

`_$HogeNotifier`に実装される`runBuild`メソッドの有無がnullの強制アンラップエラーを起こすまで

0. 前提として`AsyncNotifier#value`の初期値は`AsyncLoading`(実装上は`AsyncValue.loading()`)になっている
1. `ProviderElement#mount`（あるいは`_performRebuild`）では`ProviderElement#buildState`を呼び出す
2. `ProviderElement#buildState`では`$ClassProviderElement#create`を呼び出す
3. `$ClassProviderElement#create`では下記の分岐が存在する
   - `overrideWithBuild` によって`build`が`override`されている場合：`$ClassProviderElement#handleValue`を呼び出す
   - そうではない場合：`AnyNotifier#runBuild`を呼び出す
      - この`AnyNotifier#runBuild`を生成した`$_HogeNotifier`が`override`しており、`_$HogeNotifier#runBuild`では`$ClassProviderElement#handleValue`を呼び出している
4. `$ClassProviderElement#handleValue`は`$AsyncValueProviderElement#handleValue`で`override`されており、中では`ElementWithFuture#handleFuture`を呼び出している

### 10. overrideWithBuildの活用

Riverpod 3.0では`overrideWithBuild`が追加され、`build`メソッドだけをカスタマイズできるようになりました。
NotifierのMockを作成する代わりに、`overrideWithBuild`を使用することを推奨します。

```dart
// Before (Riverpod 2.x) - Mockを作成していた
class MockLocalUserDataNotifier extends StreamNotifier<UserData>
    with Mock
    implements LocalUserDataNotifier {
  MockLocalUserDataNotifier({required this.stream});

  final Stream<UserData> stream;

  @override
  Stream<UserData> build() {
    return stream;
  }
}

final container = createContainer(
  overrides: [
    localUserDataProvider.overrideWith(
      () => MockLocalUserDataNotifier(
        stream: Stream.value(UserData(...))
      )
    )
  ]
);


// After (Riverpod 3.0) - overrideWithBuildを使用
final container = ProviderContainer.test(
  overrides: [
    localUserDataProvider.overrideWithBuild((_, __) => Stream.value(UserData(...))),
  ]
);
```

どうしても`build`以外のメソッドをMockしたい時だけ、上記のMockNotifierを活用しましょう。`build`以外のメソッドをMockする必要があるときは、そのメソッドの中で活用しているであろう、RepositoryやProviderをMock/Overrideすることで解決できないか検討しましょう。

### 11. 自動リトライ

`overrideWithBuild`の中で例外をスローしても、ProviderContainerのretryが機能するため、直ちにAsyncErrorにならないことがあります。
テストでは、retryを無効化することで直ちにAsyncErrorになるよう変更できます。

```dart
final container = ProviderContainer.test(
  overrides: [
    localUserDataProvider.overrideWithBuild((_, __) {
      throw Exception('Could not find the user data!');
    })
  ],
  retry: (retryCount, error) {
    // 常にリトライを行わないようにする
    return null;
  }
);
```

#### TimeoutExceptionへの対応

FutureProviderの`build`で例外がスローされたときの挙動を確認するテストで、以下のエラーに遭遇しました。

```
TimeoutException after 0:00:30.000000: Test timed out after 30 seconds.
```

これは、retryがデフォルトで最大約50秒かかるためです。Dartのテストは特に指定がない場合30秒でタイムアウトします。

<https://pub.dev/packages/test#timeouts>

テストでは、retryを無効化することで解決できます。

```dart
final container = ProviderContainer.test(
  overrides: [...],
  retry: (retryCount, error) {
    // 常にリトライを行わないようにする
    return null;
  }
);
```

### 12. keepAliveとautoDisposeの関係(riverpod_lint)

keepAliveのProviderが依存するProviderは、すべてkeepAliveとしてマークする必要があります。

keepAliveのProviderAがautoDisposeのProviderBに依存している場合、警告が表示されます。

取る選択肢は2つです：

- ProviderAをautoDisposeに変更する
- ProviderBをkeepAliveにする

もしProviderBがProviderCに依存している場合、ProviderCも同様に対処する必要があります。

### 13. UnmountedRefExceptionとその対処

Riverpod 3.0では、Providerのライフサイクル管理が厳格になり、`UnmountedRefException`が発生しやすくなりました。

#### エラーの内容

```
threw StateError:<Bad state: The provider hogeProvider was disposed during loading state, yet no value could be emitted.>
```

```
threw UnmountedRefException:<Cannot use the Ref of hogeProvider after it has been disposed.>
```

どちらも意図しないタイミングでProviderがdisposeされて、Refが使えなくなったことを示すエラーです。

#### 発生箇所

以下のような箇所で発生します：

- `await ref.read(hogeProvider.future)`を利用している箇所
- Providerの外で非同期処理の中でRefを使えるようにしている箇所（`final Ref`で検索すると見つけやすい）

```dart
class Service {
  const Service(this.ref);

  final Ref ref;

  Future<void> store(Entity entity) async {
    final hogeRepository = ref.read(hogeRepositoryProvider);
    await hogeRepository.store(entity.hoge);
    // ここでUnmountedRefExceptionが発生する可能性がある
    final fugaRepository = ref.read(fugaRepositoryProvider);
    await fugaRepository.store(entity.fuga);
  }
}
```

#### 対処方法1：readFirstの実装

Riverpodの開発者であるRemiさんは、`await ref.read(hogeProvider.future)`とするのをやめて、以下のように書き換えることを推奨しています。

<https://github.com/rrousselGit/riverpod/issues/3745>

```dart
final subscription = ref.listen(hogeProvider.future, (p, n) {});
final value = await subscription.read();
subscription.close();
```

以下のようなextensionを作成すると便利です。

```dart
import 'package:hooks_riverpod/hooks_riverpod.dart';
import 'package:hooks_riverpod/misc.dart';

extension RefExtension on Ref {
  Future<T> readFirst<T>(Refreshable<Future<T>> listenable) async {
    final subscription = listen(listenable, (p, n) {});
    try {
      return await subscription.read();
    } finally {
      subscription.close();
    }
  }
}

extension WidgetRefExtension on WidgetRef {
  Future<T> readFirst<T>(Refreshable<Future<T>> listenable) async {
    final subscription = listenManual(listenable, (p, n) {});
    try {
      return await subscription.read();
    } finally {
      subscription.close();
    }
  }
}
```

命名は以下を参考にしました：
<https://github.com/rrousselGit/riverpod/issues/4339#issuecomment-3553945908>

#### 対処方法2：ref.mountedの活用

Providerがdisposeされていた場合、後続の処理を実行しなくても良いケースでは、`ref.mounted`を用いてスキップすることでエラーを回避できます。

<https://riverpod.dev/ja/docs/whats_new#refmounted>

```dart
() async {
  final value = await fetch();
  if (ref.mounted) {
    final repository = ref.read(repositoryProvider);
    await repository.store(value);
  }
}
```

#### テストと本番の挙動の違い

テストでは以下のように書くことが多いです。

```dart
final container = ProviderContainer();
addTearDown(container.dispose);
final useCase = container.read(signInUseCaseProvider);
await useCase();
```

この`addTearDown(container.dispose)`が重要です。これはテストの終了時になって初めてcontainerをdisposeします。

しかし、本番ではRiverpod 3.0からはProviderが必要とされなくなったら直ちにdisposeされます。このdisposeタイミングの違いが、テストと本番の挙動の違いになっています。

<https://github.com/rrousselGit/riverpod/blob/f4c59d00f2eed63267cb46d23335000cf44341dc/packages/riverpod/lib/src/core/provider_container.dart#L810-L826>

:::message alert
**だからテストが全部通ったからといって、動作確認を怠ったままマージしてはいけません。**
:::

#### classにRefを持たせる実装の廃止

今回、Riverpod 3.0になって期待通りに動かないことによって、classにRefを持たせる実装を変更する必要に迫られました。

しかし、これをきっかけに、**Riverpodは状態管理とDIの「ツール」であり、UseCase/Service/RepositoryといったUIと関係のないロジック部分に採用するべきではない**と再認識しました。

ビジネスロジックのテストにProviderContainerを用いなければならないのだとしたら、それはビジネスロジックの実装として適切ではありません。

何らかの理由でRiverpodをアプリから剥がしたいとなったとき、ロジック部分がそのまま利用し続けられるような実装が理想です。

参考：

- <https://zenn.dev/caphtech/articles/riverpod-business-logic-ref-guide>
- <https://zenn.dev/chooyan/articles/eefc76dbd2ba25>

:::message
この項目については、まだ整理が必要です。具体的な移行手順やBefore/Afterのコード例を今後追加する予定です。
:::

## まとめ

Riverpod 3.0への移行では、以下の点が主な変更点でした：

1. **命名規則の変更** - NotifierProviderの生成名が変更
2. **依存関係の明示** - @Dependenciesアノテーションの追加
3. **テスト周りの改善** - ProviderContainer.test()やoverrideWithBuildの追加
4. **ライフサイクル管理の厳格化** - UnmountedRefExceptionへの対処が必要

特にUnmountedRefExceptionへの対応は、Riverpodをどのレイヤーで使用すべきかを見直す良い機会となりました。

移行作業では、まず明確な変更点（1〜8、11、13）に対応し、その後にテスト周りの調整やアーキテクチャの見直しを行うと進めやすいでしょう。
